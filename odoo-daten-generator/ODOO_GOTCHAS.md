# Odoo API Gotchas — odoo-daten-generator

Live-tested field/behavior quirks vs target Odoo instance (saas-19.4). Moved out `CLAUDE.md` keep session load small. Ref from `CLAUDE.md`'s "Odoo API Conventions" section — read before touch any field not covered there.

---

**Verified field gotchas (live-tested):**

- `hr.leave` needs `request_date_from`/`request_date_to` (date) **alongside** `date_from`/`date_to` (datetime) — omit = default today, spurious overlap errors.
- `hr.leave` leave type field is `work_entry_type_id` (→ `hr.work.entry.type`), not `holiday_status_id`.
- `mail.activity.date_deadline` is **required** — always set it.
- `mail.activity.res_model_id` is Many2one → `ir.model` (writable); `res_model` is readonly/computed — never set it manually.
- `message_post` on `crm.lead`: use `client.call_method('crm.lead', 'message_post', ids=[id], kwargs={...})`.
- Leads feature flag: `ir.config_parameter` key `crm.use_lead`, value `'1'` = enabled; missing key = disabled.
- `odoo_actions.get_enabled_features(client, installed_modules)` — **without** `installed_modules` set, probes all skip, result `{}`. Always pass set.
- `hr.job.skill` / `hr.applicant.skill`: `skill_level_id` **required**, cannot be `False`/omitted — `hr.skill.type` w/ no `hr.skill.level` records can't attach to job/applicant at all. Skip skill entirely (don't build line) when no level exists.
- `hr.leave/action_approve` fails `UserError: "You cannot approve this leave."` when record already `state='validate'` — happens on creation itself for `hr.work.entry.type` records w/ certain `leave_validation_type` values (e.g. `'both'`), auto-validate on create for API-key user. Check `state` before calling `action_approve`, don't call unconditionally.
- `hr.leave.allocation` has **no** `allocation_type` field on saas-19.4 (existed 19.2, since removed — accrual vs regular now implied by `accrual_plan_id` set or absent). Don't send it.
- `ir.attachment` binary content field `raw`, **not** `datas` — `datas` doesn't exist as field here at all (`search_read` raises `Invalid field 'datas' on 'ir.attachment'`), yet `create()` silently accepts+drops `datas` key instead of raising (200 OK, no content stored, no error). `db_datas` also in `fields_get` but write direct = silently dropped too (attachments filestore-backed here, not DB-column-backed). Only `raw` round-trips actual file content on create/read.
- `product.template`/`product.product`: enable Odoo's native "auto-create Project+Task on order confirmation" needs **three** independent fields, not two — `service_tracking='task_in_project'` (creates Project+Task), `invoice_policy='delivery'` (invoice delivered not ordered qty), **and** `service_type='timesheet'` (field that actually makes `sale.order.line.qty_delivered_method` become `'timesheet'`, easy miss since doesn't follow from other two). Don't use convenience field `service_policy` — it's `store: false` (UI-only onchange helper), may silently drop on `create()` here, same trap class as `ir.attachment.datas`.
- `account.move.line.sale_line_ids` (m2m → `sale.order.line`) **readonly** — can't set on `account.move`/`account.move.line` `create()`. Writable reverse side `sale.order.line.invoice_lines` (m2m → `account.move.line`) — but as of Sprint S7/R8, invoicing goes thru `sale.advance.payment.inv` wizard instead, sets this link server-side natively; no manual write needed either way.
- Invoice `sale.order` way Odoo's own "Create Invoice" button does: create `sale.advance.payment.inv` record (`advance_payment_method='delivered'`, `sale_order_ids=[(6,0,[order_id])]`), then `call_method('sale.advance.payment.inv', 'create_invoices', ids=[wizard_id])` — this public method (no leading underscore) callable via JSON2 even tho wraps private `sale.order._create_invoices()`. Read back created invoice(s) via `sale.order.invoice_ids` (m2m → `account.move`) after — method's own return value `ir.actions.act_window` dict, not usable direct. Single order w/ nothing currently invoiceable (e.g. delivery-policy line w/ `qty_delivered=0`) makes call raise for that order; call wizard **per order**, not once for whole batch, so one such order don't drag every other invoiceable order in batch into fallback with it — live-confirmed multi-order batch does NOT raise as whole when only some orders empty, but solo empty-order call does.
- `RunContext.company_ids` (`config.py`) misleadingly named: despite "company", holds **`res.partner`** IDs — customer/company contacts `master_data.py` creates via `client.create_batch('res.partner', ...)` — **never** real `res.company` ID. `sale.py` already uses `ctx.company_ids[i]` correct as `sale.order.partner_id`; `mrp.py:282,334` does not (passes `ctx.company_ids[0]` as `company_id` to `mrp.workcenter`/`get_manufacturing_picking_type_id`, silently degraded behind broad try/except — likely live pre-existing bug, not fixed as of S8). Wherever actual `res.company` ID needed (e.g. `stock.warehouse`/`purchase.order`/`stock.quant` `company_id`), use `odoo_actions.get_main_company_id(client)` instead (added S8) — never `ctx.company_ids[0]`.
- Odoo's JSON/2 **error object** is `{"name", "message", "arguments", "timestamp", "context", "debug"}` — `debug` carries full server-side traceback w/ `/home/odoo/src/...` paths. `odoo_client._redact_error_body` takes only `message`; nothing else crosses into log or `self.errors`.
- Odoo SaaS prefixes some error messages w/ runs of **invisible characters** (zero-width joiners, variation selectors `U+FE00–FE0F`, tag characters `U+E0000–E007F` — tracing watermark). Makes real message unreadable in log; `odoo_client._printable` strips them (category `Cf` alone not enough — variation selectors are `Mn`).
- `requests.Session` has **no** `allow_redirects` attribute (`__attrs__` carries `max_redirects` only), so session-level assignment silent no-op — must be per-request kwarg at every `session.post` call site. Also note `raise_for_status()` ignores 3xx: unfollowed redirect falls thru to `response.json()` as opaque JSONDecodeError unless explicit reject (`odoo_client._reject_redirect`).
- **JSON2 payload-format fallback chain — removed.** `odoo_client.py` used to try `/call_kw/<model>/<method>` and `/call/<model>/<method>` as fallback paths for `create`/`write`/`call_method`/`model_method`, plus `args`/`kwargs`/`values` as alternate payload shapes. Neither fallback path got single recorded success anywhere in repo history. Confirmed live, independently, twice: both fake paths 404 w/ `"Did you mean POST /json/2/<model>/<method>?"` unconditionally — even *before* Odoo's own auth check runs (direct `/<model>/<method>` form 401s on bad key; `/call/...`/`/call_kw/...` 404 regardless of key). JSON-2 exposes exactly one route per model+method, dispatches by matching JSON keys to target method's own param names — no positional-args concept. Every real call site already hit first (only real) format on happy path. `call_method` no longer takes `args` param (0 of 15 call sites used it) — caller still passing it gets `TypeError` at call site. Each of five core methods now sends exactly one request.
- `client.errors` gets **one entry per failed logical operation**, not one per HTTP attempt (`odoo_client._record_failure`) — before chain removal meant up to eight entries for one failed call, why 8 of 14 errors in live report turned out planned 404 probing, not real failures. `run_journal._first_new_error` (mark-and-diff over `client.errors`) still exists+works, now mostly relevant for `_post`'s own 401-retry sub-attempts rather than cross-method chain.
- `POST /json/2/<model>/has_access` w/ `{"ids": [], "operation": "create"}` (**named** payload key — `args=[...]` rejected) answers whether API-key user may create records on `model`: `true`/`false` for real model, `404` if model don't exist. `check_access_rights` gone on saas-19.4; `has_access` successor. Answers *write*-access question `search_read`/`fields_get` can't: on `demo-test5`, **read** probe on `mrp.workcenter` reported `True` while "Work Orders" setting checkbox off, so run started, guaranteed fail on first work-center create. `odoo_client.has_create_access(model)` wraps this as single direct POST rather than thru `model_method`/`call_method` — those wrap every attempt in `_record_failure`, always records failure, and probing expected 404 for models that don't exist here; must not clutter error report way real operation's failure does. Only real `403`/`404` counts as definitive "no"; `429`/`5xx`/timeout must read "unknown" (default open), or rate limit hit while probing silently disables module actually fine.
- Odoo refuses `unlink` on lot of what full run creates: posted `account.move` and every `res.partner`/`product.product` it references ("restricted audit trail"), confirmed `sale.order` ("must first cancel it"), invoiced `account.analytic.line`, `stock.quant` (no delete group for API user), `project.task.type` still referenced by tasks. Cancel first where Odoo names it (`sale.order.action_cancel`, `account.move.button_draft`+`button_cancel`); expect rest stay.
- **Groq retires models w/o notice.** `llama-3.3-70b-versatile` 404s as of 2026-08-28; repo default now `qwen/qwen3.8-27b`. `openai/gpt-oss-120b` pings fine but truncates JSON responses `fetch_name_suggestions` needs — working ping not proof model usable.
- Live SaaS instance **rate-limits w/ HTTP 429**: sustained write rate ~**1 req/s**, token bucket absorbs burst on top (~150 requests in ~15s measured 2026-08-28), answered by bare HTML 429 w/ no `Retry-After`. *The* reason codebase batches everywhere — `create_batch`, D3, test Pattern 8. **Never answer 429 by retrying inside loop that shoulda been one batched call.** `odoo_client._send` adds bounded exponential backoff (5 attempts, `Retry-After` honoured when sent) as safety net for calls batching can't remove; without it every module after ceiling fails w/ `429 Client Error` in way reads like code defect. Space heavy runs out before blame code.
- `purchase.order.action_create_invoice` creates vendor bill w/ `invoice_date` unset (`False`) — it's vendor's own external date, Odoo sets no default. `account.move.action_post` then raises `UserError: "Das Datum der Rechnung/Erstattung ist erforderlich..."` (invoice date required). Write `invoice_date` (e.g. `datetime.date.today().isoformat()`) on bill before posting — manual `account.move` rebuild fallback already sets it, only `action_create_invoice` path needs extra write.
- `hr.job.payment_interval` failure carried since S10 Phase A **misdiagnosed as field-schema issue**; real cause: `hr_recruitment` itself `state=uninstalled` on `demo-test5` (live-confirmed via `ir.module.module`) — `payment_interval` exists fine in Odoo's own `hr.job` schema, just unreachable cuz whole recruitment app ain't there, and `hr.applicant` don't exist as model at all here. `orchestrator.py:75` already gated `create_recruiting_data` on `"hr_recruitment" in ctx.installed_modules` before this fix — production code never actually broken. Bug was two live-integration test files calling low-level recruiting helpers direct, bypassing that gate: `tests/integration/test_recruiting.py` (steps 1/2/4/7) and `tests/integration/test_documents.py` (its setup's applicant creation + P2 CV-PDF step) both needed same `'hr_recruitment' in ctx.installed_modules` skip `test_hr.py` already used for `hr_holidays`/`hr_work_entry` in S10 Phase A — `test_recruiting.py` alone not enough, `test_documents.py` has independent unguarded call site.
- **S13/WP1 (stock.warehouse/stock.location/stock.lot, live-verified 2026-09-02):** minimal `stock.warehouse.create({name, code, company_id})` enough — Odoo auto-fills `view_location_id`/`lot_stock_id`/routes server-side despite both `required: true`, no need send em. `tracking='lot'`/`'serial'` write/read fine on both `product.product` and `product.template`. `stock.lot` name collision on `(company_id, product_id, name)` real (rejected) — irrelevant here since this repo's lot names embed the product's own id (`LOT-{pid}-0000`), collision-proof by construction. `stock.location.barcode` and `product.product.barcode` **separate namespaces** — no cross-model dedup needed. `action_apply_inventory` works fine on lot-tracked quant and on a batch of serial quants (qty 1 each).
- **Archive-fallback asymmetry (`active=False` when `unlink` fails, S13/R14+R15):** `stock.warehouse` archives fine **even with contained stock** — `active` independent of its locations' own state. `stock.location` archive **fails the same way unlink does** while it still holds a `stock.quant` (same German error, "... enthält noch Produkte ..."). `stock.lot` has **no `active` field at all** — no archive fallback possible, unlink failure on a referenced lot is permanent residue, accepted limitation (see `run_journal.ARCHIVE_FALLBACK_MODELS`).
- Reading current `res.config.settings` values (e.g. `group_stock_multi_locations`, `group_stock_production_lot`) over JSON2: `client.create('res.config.settings', {})` (transient wizard model, empty vals) then read back the computed defaults on the returned id — works fine live, no separate "get settings" endpoint needed. Run this through the plain client, not a `JournalingClient`, or the transient record gets journaled for a cleanup pass that will never find it (`res.config.settings` records don't persist across requests the normal way).
- **S14/WP1+WP4 (`stock.warehouse.orderpoint`/`quality.point`/`quality.check`, live-verified 2026-09-03):** `stock.warehouse.orderpoint.warehouse_id` — never set, Odoo derives it correctly from `location_id`; `name` — required+readonly, auto-filled via sequence, never set. Live-confirmed unique constraint on `(product_id, warehouse_id, location_id)`. `quality.point.test_report_type` selection is **`pdf`/`zpl` only** — `'none'` (this repo's prior value) 500s with `Wrong value for quality.point.test_report_type: 'none'`, and had never once succeeded (masked by a broad `except Exception`, only test path left the feature off by default). `quality.point.bom_id` is a compute facade — silently discarded on write, even with a valid id; the real, writable link to a BOM's product is `apply_to='products'` + `product_ids` (both real fields, `apply_to` required). `quality.point.measure_on` / `quality.check.measure_on` **don't exist** on this instance's Quality install despite the `odoo-fields` MCP tool's cache showing both as required — cache reflects a fuller Quality-Control install than what's actually live here (also carries phantom `spreadsheet_id`, `obox_device_id`, `measure_frequency_*`, `norm`/`tolerance_min/max`, etc. — treat all of it as cache noise, not just `measure_on`). `quality.check` model itself genuinely exists (67 real fields) — only the fuller-install-only fields are the gap. `quality.check.do_pass`/`do_fail` are real, callable in batch (`ids=[...]`) — correctly set `quality_state`/`control_date`/`user_id`; prefer over writing `quality_state` directly at `create()` (native-over-manual, matches `action_apply_inventory`/`action_confirm` elsewhere). Odoo does **not** auto-generate a `quality.check` on `mrp.production.action_confirm` alone even when a matching `quality.point` already exists — only at `stock.picking` validation, which this codebase never reaches.
- **S16 spike (`res.company`/multi-company, live-verified 2026-09-04):** a fresh `res.company.create()` has **no** chart of accounts (`account.account` count 0) **unless `country_id` is set at create time — see the superseding finding below.** Manual loading over JSON2 still works if ever needed for a company created without a country: `client.call_method('account.chart.template', 'try_loading', ids=[], kwargs={'template_code': 'de_skr03', 'company': <id>})` — an `@api.model` classmethod, `ids=[]` works. Two live-found preconditions for the manual path: (a) `res.company.country_id` must be set **before** the call, else `"Missing required field 'Country' ... for model 'Tax'"`; (b) template and country must actually match — `template_code='generic_coa'` with `country_id`=Germany fails with `"The tax group must have the same country_id as the tax using it"`, `template_code='de_skr03'` with Germany works. The chart-load records (`account.account`/`account.journal`/`account.tax`/...) are created server-side and never pass through this repo's `JournalingClient` — D7's `delete_run` cannot ever clean them up, regardless of `ARCHIVE_FALLBACK_MODELS` — true for both the manual and automatic path below.
- **`country_id` set AT `create()` time auto-provisions a full chart of accounts — simpler than the manual recipe above, live-verified 2026-09-04.** `client.create('res.company', {'name': ..., 'country_id': <DE id>})` — no `try_loading` call at all — comes back with a complete, real CoA already loaded: 1312 `account.account`, 8 `account.journal`, 12 `account.tax`, 6 `account.fiscal.position`, `chart_template` auto-set to `'de_skr03'`. This is Odoo's own `res.company.create()` override reacting to `country_id` being present in the creation vals. **Order matters and there's no retroactive path:** `country_id` written via `write()` **after** `create()` (even immediately after, on an otherwise-empty company) provisions **nothing** — 0 accounts, `chart_template` stays `False`. Always pass `country_id` inside the `create()` vals dict itself, never as a follow-up write, if a chart of accounts is wanted.
- **No company-based record-rule enforcement observed for the standard API-key user (`res.users` id 2, `company_ids=[1]`), live-verified 2026-09-04.** Naively expected: an unfiltered `search_read` (no domain) should hide records belonging to a company outside `allowed_company_ids`, same as the Odoo UI would for a regular user. Live-tested with a fresh company + warehouse: `search_read` with an `id` domain, a `company_id` domain, and **completely unfiltered** (`limit=0`) all returned the same record — no masking in any shape. (An earlier same-day probe wrongly concluded masking was real; that was a `limit=20` truncation artifact — the target record's id simply sorted past position 20 — not a record rule. Always re-test with `limit=0` before concluding a record is invisible.) Root cause not chased further (plausibly this API key belongs to a privileged/internal user whose access bypasses standard multi-company record rules) — but do not assume `company_ids` restricts what this API key can read/write/create, in any query shape, on this instance. Practical consequence: code that creates records under a second `res.company` (e.g. `modules/multicompany.py`, S16) must not rely on this masking for isolation — `connect_service.fetch_existing_data`'s unfiltered `product.product`/`res.partner` queries (`connect_service.py:109-124`) will surface a second company's records to any later run just as readily as the first company's, so anything creating multi-company records needs its own explicit `company_id` filtering downstream, not implicit protection from Odoo.
- `res.company.active` (boolean, `readonly: false`) works as an archive fallback even when the company already holds referenced records (e.g. a `stock.warehouse`) — `write('res.company', [id], {'active': False})` succeeds where `unlink` is refused by FK constraints (`account_fiscal_position_company_id_fkey`, `stock_picking_type_company_id_fkey` observed live). `res.company.create()` also auto-creates a linked `res.partner` (its own `partner_id`, required) server-side — that partner never passes through `JournalingClient.create` either, same uncleanable-residue class as the chart-of-accounts records above, just smaller.
- **Transactional records under a non-primary company work fine with company-neutral (`company_id=False`) partners/products — live-verified 2026-09-04.** Created a `sale.order` with `company_id=<fresh, second company>`, `partner_id` and `product_id` both left at their default `company_id=False` (this repo's `master_data.py` never sets `company_id` on partners/products it creates) — `create()` **and** `action_confirm()` both succeeded, no company-mismatch error. Odoo's multi-company model only restricts records already scoped to a *different* company (see the reassignment-refusal finding above); a never-scoped, company-neutral record is usable across any number of companies' documents. Practical consequence for a multi-company demo-data feature: additional companies do **not** strictly need their own dedicated partners/products — sharing today's company-neutral master data across all target companies' transactional records is a live-confirmed option, not just a theoretical one. Distinct per-company catalogs remain a realism choice, not a technical requirement.
- **`res.company.create()` does NOT auto-create a `stock.warehouse`**, live-verified 2026-09-04: fresh company, no other action taken, `search_read('stock.warehouse', [['company_id','=', <new id>]])` immediately afterward returns `[]`. Don't assume Odoo seeds a default warehouse per company the way it seeds a `res.partner` (see above) — any code that wants one for a second company has to create it explicitly (`odoo_actions.create_second_warehouse(client, company_id)`, R14).
